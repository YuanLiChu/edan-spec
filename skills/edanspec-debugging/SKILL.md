# 调试与排障

结构化定位和修复问题。**先理解再动手，一次修一类。**

本 skill 可独立执行——遇到测试失败、编译错误、运行时异常或行为不符预期时直接调用。

## 五步排障流程

```
1. 观察（Observe）→ 收集完整错误信息
2. 复现（Reproduce）→ 确认错误可稳定复现
3. 定位（Locate）→ 找到根因，不是表面症状
4. 修复（Fix）→ 最小改动，只修根因
5. 验证（Verify）→ 确认修复有效且无副作用
```

---

## 步骤一：观察

**不要只看第一行报错。**

收集完整信息：
1. 错误类型（AssertionError / NullPointerException / 编译错误 / 超时）
2. 完整错误消息（expected vs actual）
3. 堆栈跟踪（从栈顶到第一个自己写的代码行）
4. 失败时的输入数据（参数值、Mock 配置、环境变量）
5. 最近的代码变更

> **常见错误**：只看 "test failed" 就开始改代码，不看具体错误信息和栈跟踪。

---

## 步骤二：复现

只运行失败的测试/命令，确认每次都能复现。

**不能稳定复现 = 还没有真正理解问题。**

| 场景 | 复现方式 |
|------|---------|
| 单元测试失败 | 只运行该测试 |
| 编译错误 | 运行完整编译 |
| 运行时异常 | 用相同输入触发 |
| 间歇性失败 | 连续运行 3-5 次 |

---

## 步骤三：定位

### 编译错误

| 子类型 | 常见原因 | 定位方法 |
|--------|---------|---------|
| 类型不匹配 | 返回值/参数类型错误 | 看编译器指出的具体行 |
| 找不到符号 | import 缺失/拼写错误 | 搜索符号定义 |
| 循环依赖 | 两个类互相引用 | 检查 import 关系 |

### 逻辑错误（断言失败）

```
1. 读测试代码 → 理解期望行为
2. 读实现代码 → 理解实际行为
3. 对比 expected vs actual → 定位差异点
4. 追踪数据流 → 找出差异产生的具体位置
```

**常见根因**：逻辑反转、边界遗漏、空指针、Mock 错误、依赖未注入。

### 运行时异常

```
1. 从堆栈跟踪找到第一个自己写的代码行
2. 读该行代码和上下文
3. 确认哪个值为 null / 哪个条件不满足
4. 追踪该值的来源（参数？返回值？字段初始化？）
```

### 行为不符预期（无报错但结果不对）

```
1. 确认输入和预期输出
2. 追踪数据流（输入 → 处理 → 输出）
3. 在关键节点添加临时日志/断点
4. 找到第一个偏离预期值的点
```

## 步骤四：修复

**核心规则：只修根因，不修表面症状。**

```kotlin
// 以下以 Kotlin 为例
// 错误：修了测试而非代码
assertEquals(10.0, result) // 把期望值改为错误的值来"通过"

// 正确：修复业务代码
return items.sumOf { it.price * it.quantity } // 修复计算逻辑
```

**修复前问自己**：
1. 这个修改直接解决了根因吗？
2. 这是最小的修改吗？（能加一行而不是改十行？）
3. 会影响其他不相关的测试吗？
4. 我是在修代码还是在"让测试通过"？

详见 `references/fix-strategies.md`。

---

## 步骤五：验证

1. 原来失败的测试/命令现在通过了
2. 相关的其他测试不受影响（跑完整测试套件）
3. 没有引入新的编译错误
4. 没有引入新的警告
5. 代码风格和质量检查通过

**只在一个条件下验证通过 ≠ 修复完成。**

---

## 修复上限

| 次数 | 应该做什么 |
|------|-----------|
| 第 1 次 | 正常修复，按五步流程 |
| 第 2 次 | 正常修复，但检查是否理解有误 |
| 第 3 次 | 停下来：根因找错了？重新定位 → 调 `edanspec-debugging` 深度排查 |
| 第 4 次 | 严重警告：设计可能有根本问题 → 调 `edanspec-explore` 重新审视设计方案 |
| 第 5 次 | **停止修复**，报告问题，调 `edanspec-explore` 重新审视设计方案（如有上游文档则调 `edanspec-task-plan` 重新规划） |

**次数从修复尝试计数**：每次修改代码后验证仍失败，计为一次。同一问题修复超过 2 次未成功应停下来重新定位根因（第 3 次）；超过 3 次应调 `edanspec-explore` 重新审视设计方案（第 4 次）；第 5 次停止并报告问题。

## 常见误区与反驳

> 通用误区见 `AGENT.md`。

| 说辞 | 真相 |
|------|------|
| "先改一行试试看有没有好" | 盲目修改 = 把 bug 从显式变成隐式 |
| "测试期望值可能错了，改一下测试吧" | 修改测试来适应错误代码 = 把 bug 合法化 |
| "这个错误我以前见过，直接套用" | 同样的症状可能是不同的根因 |

## 需要警惕

- 改了一行就跑一次，反复多次（不是系统性定位）
- 修改测试来让错误代码"通过"
- 修了一个失败但出现了两个新失败
- 修复循环超过 3 次还在继续
- 不知道根本原因就开始修改代码
- 同时修改多个地方，不知道哪个是真正的修复

## 验证

- [ ] 已收集完整错误信息
- [ ] 错误已稳定复现
- [ ] 根因已定位（不只是表面症状）
- [ ] 修复是最小改动
- [ ] 原来失败的测试现在通过了
- [ ] 相关测试套件未被破坏
