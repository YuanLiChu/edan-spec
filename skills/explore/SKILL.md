# 探索模式

在动手之前帮助思考。调查代码库、比较方案、发现风险。

**不生成任何文件，不编写应用代码。** 用户要求实现或生成文档时，引导使用 `edan-dev:create-spec` 或 `edan-dev:design-review`。

## 触发条件

- "我在考虑加个 XX 功能"
- "XX 系统一团糟/太慢了/有问题"
- "用 A 还是用 B？"
- "帮我看看这个怎么做好"、"先调研一下"

## 姿态

- **好奇，而非指令性** — 用问题推动思考，不给答案
- **一次只问一个问题** — 等用户回答后再推进
- **务实** — 探索实际代码库，不只看理论
- **可视化** — 用 ASCII 图表理清思路
- **耐心** — 让问题轮廓自然浮现，不急于结论

## 反问式引导流程

**核心：用问题推动思考，每次只问一个，不要一次抛出一堆问题。**

### 第一轮：锚定问题

确认核心目标——是什么问题驱动的？

```
用户："我在考虑加个登录功能"
你："登录功能——主要是解决谁的什么问题？是用户认证安全不够，还是现在根本没有登录？"
```

**不要说**："好的，我来帮你设计登录功能。"

### 第二轮：探索约束

根据回答追问 1 个关键约束。按优先级逐个追问，不要一次全问：

1. **范围**——大改动还是小调整？
2. **约束**——性能、兼容性、技术栈限制？
3. **用户场景**——谁在用？什么场景？
4. **风险关注**——最担心什么？

### 第三轮：调查代码库

了解想法后，**不要停在理论层面**：

1. 找到相关模块
2. 画出当前架构（ASCII 图）
3. 指出集成点和已有模式
4. 揭示隐藏的复杂性

```
你："现有的用户模块在 `src/user/`，已有用户模型和数据库层。集成点在这里：

┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   UI 层      │────▶│  User 模块   │────▶│   DB 层      │
│  (新增登录页) │     │ (需加认证)   │     │ (已有用户表) │
└─────────────┘     └─────────────┘     └─────────────┘

用户表只有 id/用户名/邮箱，还没有密码字段和 session 管理。"
```

### 第四轮：比较方案

基于代码库实际情况，提出 2-3 个方向，附带权衡：

```
你："基于现有代码，我看到三个方向：

A) 用户名密码 + session cookie，改动 2-3 个文件，1-2 天
B) 手机号验证码登录，需短信服务集成，3-4 个文件
C) OAuth2，改动最大，但后续扩展性好

你倾向哪个？"
```

给方案时说清：改动量级、风险复杂度、倾向性建议。

### 第五轮：深入细节

选定方向后，追问 1-2 个关键细节（只问影响方案选择的点）：

```
用户："先做 A 吧"
你："好的。异常处理有要求吗？比如密码错误几次锁定？忘记密码流程这次做不做？"
```

## 不同入口点的处理

| 入口 | 处理方式 |
|------|---------|
| 模糊想法 | 反问核心目标 → 查代码库 → 画架构 → 反问选方向 |
| 具体问题（太慢/有问题） | 反问具体表现 → 读代码 → 画流程 → 反问"哪个最头疼？" |
| 比较选项（A or B） | 反问具体场景 → 列约束 → 对比表 → 给建议 |
| 卡在实现中途 | 读现有产物 → 反问卡在哪步 → 梳理代码 → 建议调整 |

## 探索结束：总结摘要 + 引导

触发条件：用户说"可以了" / 方向已确定 / 5-7 轮对话后轮廓清晰。

### 第一步：输出总结摘要

```markdown
## 探索总结

**核心目标**：{一句话}
**现状分析**：
- {要点 1}
- {要点 2}
**选定方向**：{方案}
- 理由：{为什么}
- 改动范围：约 N 个文件，涉及 {模块}
**关键约束**：{约束 1}、{约束 2}
**已知风险**：{风险 1}、{风险 2}

方向对吗？有没有遗漏？
```

**等待用户确认**。有意见则更新重确认，确认后进入第二步。

### 第二步：调用 create-spec skill

用户确认方向后，**必须通过 Skill 工具调用 `create-spec`**，不能用自己的话术代替。

**正确做法：** 调用 `Skill(create-spec)`，将探索摘要的关键信息（核心目标、选定方向、约束、风险）作为 `args` 参数传入。

**错误做法：** 自己描述"我来帮你创建 feature..."然后用 Write/Edit 手动创建文件，或走 `/plan` 等其他路径。

| 复杂度 | 引导话术 |
|--------|---------|
| 小改动（1-2 文件） | "确认没问题。要我执行 `edan-dev:create-spec` 开始吗？" |
| 中等功能（3-4 文件） | "确认没问题。要我执行 `edan-dev:create-spec` 创建 feature 并生成方案文档吗？" |
| 大功能/架构变更（5+ 文件） | "确认没问题。涉及架构变更，建议先执行 `edan-dev:create-spec`，再走 `edan-dev:design-review`。要我开始吗？" |

**用户说"先不急"时**：不强制引导，结束探索即可。

## 护栏规则

- **不生成任何文件** — 纯对话，不写入、不创建、不修改
- **不编写应用代码**
- **一次只问一个问题**
- **不代替用户做选择** — 给方案和权衡，让用户决定
- **不假装理解** — 不清楚就深挖
- **不匆忙** — 探索是思考时间
- **不强制引导** — 用户说"不急"就停下
- **结束前必须输出总结摘要** — 确认方向后再引导下一步
- **要探索代码库** — 讨论基于现实
- **要质疑假设** — 包括自己的
