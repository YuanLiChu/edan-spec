# 技术设计（design.md）编写规范

`design.md` 由 `create-spec` 生成，位于 `.edan-dev/feature/<name>/design.md`。本规范定义其决策记录格式，供生成时参考。

## 文档结构

`design.md` 采用以下章节结构，生成时按需裁剪（如不涉及数据变更可省略数据模型章节）：

```markdown
# {功能名称} 技术设计

## 背景

当前系统的状态、为什么要做这个改动、现有的问题或机会。
1-2 段话即可，重点说清楚"为什么是现在"。

## 设计目标与范围排除

**设计目标：**
- [本次要达成的具体技术指标，需可量化、可验证]
- [示例：用户登录请求 P95 响应时间 < 500ms]

**范围排除：**
- [明确声明不属于本次变更的内容，防止范围蔓延]
- [示例：本次不包含第三方 OAuth 登录（微信、Apple ID）]

## 技术决策

> 决策项参考见「技术决策记录」章节。存量项目沿用已有技术栈的决策项可简写为"沿用现有：{技术}，本次不变更"。

### 决策一：{决策项名称}

**决策**：[最终选择的具体方案]

**理由**：
- [为什么选这个，聚焦本项目相关因素]
- [不选其他的，核心短板是什么]

**替代方案对比**：
| 方案 | 优势 | 劣势 | 适用场景 |
|------|------|------|---------|
| [方案 A] | ... | ... | ... |
| [方案 B]（首选） | ... | ... | ... |

## 数据模型

[数据结构、表结构、接口协议、状态机等。不涉及数据变更时可省略]

## 接口设计

[新增或修改的 API 接口定义、参数说明、返回格式。不涉及接口变更时可省略]

## 时序与交互

[关键流程的时序图或流程图（Mermaid），帮助理解模块间交互。简单流程可省略]

## 风险与应对

- [潜在风险 1] → 应对措施或降级方案
- [已知不确定性] → 验证方式或下一步行动

## 迁移策略

[存量系统的迁移方案。不涉及数据或系统迁移时可省略]

- **数据迁移**：[迁移脚本、数据转换规则、兼容性处理]
- **过渡方案**：[如双写、灰度切换、向下兼容策略]
- **回滚方案**：[出现问题时如何安全回退]

## 测试策略

[测试覆盖的重点和范围。不涉及可省略]

- **单元测试重点**：[核心业务逻辑、边界条件]
- **集成测试重点**：[外部依赖交互、数据流完整性]
- **需要 Mock 的外部依赖**：[列出所有需要模拟的外部系统]

## 部署与发布

[上线方案。独立新功能或小型变更可省略]

- **功能开关**：[Flag 名称、默认值、控制粒度]
- **发布策略**：[全量发布 / 灰度发布 / 按用户分群]
- **回滚条件**：[什么指标异常时触发回滚]
```

### 章节说明

| 章节 | 是否必选 | 作用 |
|------|---------|------|
| 背景 | 必选 | 交代上下文，让读者快速理解"为什么要做" |
| 设计目标与范围排除 | 必选 | 定义技术指标和变更边界，防止范围蔓延和过度设计 |
| 技术决策 | 必选 | 核心章节，记录每个技术选型的决策过程 |
| 数据模型 | 按需 | 涉及数据结构、表结构、接口协议时编写 |
| 接口设计 | 按需 | 涉及 API 新增或修改时编写 |
| 时序与交互 | 按需 | 多模块交互复杂时用图表达 |
| 风险与应对 | 必选 | 提前暴露不确定性，降低开发过程中的意外 |
| 迁移策略 | 按需 | 存量系统变更时说明迁移、过渡、回滚方案 |
| 测试策略 | 按需 | 明确测试重点，防止实现阶段遗漏关键测试 |
| 部署与发布 | 按需 | 大功能上线时说明发布策略和回滚条件 |

## 技术决策记录

每个决策项包含三部分：**决策**（最终选择）、**理由**（为什么选它）、**替代方案对比**（至少 2 种方案的优劣势）。

### 必选决策项

| 决策项 | 说明 |
|--------|------|
| 架构模式 | 项目的整体架构风格（MVC/MVP/MVVM/MVI/整洁架构/BFF/微服务等） |
| 编程语言 | 使用的语言及版本，有存量项目时确认是否保持一致 |
| UI 框架 | 界面实现方式（声明式/命令式、原生/Web/跨平台） |
| 异步处理 | 并发模型选择（协程/线程池/Rx/async-await 等） |
| 依赖注入 | 依赖管理方式（编译时注入/运行时注入/手动注入/服务定位器） |
| 数据存储 | 持久化方案（关系型数据库/键值存储/文件/内存缓存） |
| 构建工具版本 | 构建工具链的版本号及其兼容性，有版本绑定要求的平台必须给出具体版本号 |

### 可选决策项

| 决策项 | 何时确认 |
|--------|---------|
| 网络请求库 | 涉及 HTTP/gRPC/WebSocket 等网络通信时 |
| 图片/媒体加载库 | 涉及图片、视频、音频等媒体资源处理时 |
| 路由/导航方案 | 多页面/多模块应用的路由策略 |
| 状态管理 | 全局状态或跨组件状态同步方案 |
| 日志/监控 | 日志框架、APM、错误上报等可观测性方案 |
| 安全方案 | 加密算法、认证协议、密钥管理等 |

## 编写要求

### 决策编写规范

- **至少两种方案对比**：每个技术决策至少列出 2 种备选方案，标注首选方案并给出具体理由
- **理由聚焦项目实际**：理由必须与当前项目的约束条件相关（如团队能力、性能要求、存量技术栈），不能泛泛而谈"社区流行"、"生态好"
- **决策可追溯**：每个决策项的名称要具体（如"决策：使用 StateFlow 而非 LiveData 管理 UI 状态"），不要用"架构"、"技术栈"等模糊标题
- **存量项目沿用优先**：已有项目默认沿用现有技术栈。沿用现有技术的决策项可简写为"沿用现有：{技术名称}，本次不变更"，仍需说明不变更的理由

### 技术选型约束

- **有上游文档时优先读取**：生成前先读取 `proposal.md`、`specs/` 中已有的约束条件，决策不能与已确认的需求矛盾
- **新项目按平台参考逐项确认**：新项目参考 `platform-{android,flutter,web,frontend,embedded}.md` 中的技术选型表，逐项确认后写入 Decisions 章节

### 文档维护

- **实现前以文档为准**：编码时必须遵循 design.md 中的决策。实现过程中发现某个决策不可行时，先更新 design.md 再继续编码
- **变更需记录理由**：design.md 生成后如果发生决策变更（如技术选型调整、范围变更），在对应决策项下追加"变更记录"段落，说明变更原因和时间
- **信息冲突处理**：design.md 与 spec 或 proposal 矛盾时，不要自行裁决——报告冲突、列出选项、等待用户决策
