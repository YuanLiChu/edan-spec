# 任务规划

把需求变成可执行的任务清单。核心原则：**按功能路径拆分，不按技术层拆分。**

## 你会做什么

### 阅读上游文档

按优先级读取上游文档，有则读，无则跳过：

| 优先级 | 文档 | 来源 |
|--------|------|------|
| 1（重量评审） | `review/solution.md` + `review/detail.md` | `edanspec-design-review` 产出 |
| 2（轻量方案） | `proposal.md` + `design.md` + `specs/` | `edanspec-create-spec` 产出 |
| 3（无方案） | 直接基于需求描述 | 无上游时 |

选择最高可用优先级作为主要输入，但依赖的低优先级文档仍需读取。

**如果连需求描述都不明确，先向用户确认范围再开始规划。**

规划阶段不写代码。

### 实现契约编译

当 `review/detail.md` 存在时，它是实现阶段的技术合同，不能只作为背景材料略读。生成任务前必须：

1. 检查契约状态为“可规划”，阻塞清单为空或全部解决。
2. 建立 `需求 ID → IC-FLOW → IC-CHANGE/IC-DATA/IC-LIFE/IC-ENG → IC-VERIFY` 映射。
3. 将实现契约中的复用锚点、文件与符号、输入输出、副作用、失败语义、修改边界和验证命令编译进对应任务卡。
4. 每个任务填写实际契约 ID，不得写“见详细设计”这类无定位引用。
5. 契约缺少真实符号、协议存在冲突或验证不可执行时，停止规划，先回到 `design-review` 更新 `review/detail.md`，不得在任务阶段自行猜测。

没有重量评审产物时，使用 `proposal.md + specs/ + design.md` 完成相同字段；无法确认的实现细节必须列为阻塞项，不能伪造代码路径或符号。

### 按可验证业务行为切片

**正确方式**（按功能垂直切分，每个任务独立可测试）：
```
任务1：用户注册功能（schema + API + UI）
任务2：用户登录功能（schema + API + UI）
```

**错误方式**（按技术层水平切分，任务之间强耦合）：
```
任务1：所有数据库表
任务2：所有 API
任务3：所有 UI
```

**切片约束**：一个任务只交付一个可独立验证的业务行为，涉及文件必须完整枚举。建议任务为 0.5～1.5 人天、验收标准不超过 3 条；超出时优先按独立业务流、状态变化或失败分支拆分，不得为了满足文件数量切断端到端链路。

跨协议、模型、UI、构建和测试的同一行为允许涉及多个文件。如果拆分后任一任务无法独立构建或验证，应合并为一个垂直切片或先安排骨架任务。

### 增量计划

每个任务内部按增量切分，增量数 = 验收标准数。按依赖顺序自底向上：
```
数据库 schema → API 模型 → API 端点 → 前端组件 → UI
```

### 工时估算

必须读取 `references/risk-classification.md` 计算缓冲工时，不得凭感觉填写。

### 模板与输出

详细模板见 `templates/task-template.md`。按模板结构生成任务卡片，每个卡片包含：描述、关联需求、实现契约引用、复用锚点、修改符号、输入输出与副作用、失败语义、修改边界、协议/字段映射、前置依赖、涉及文件、验收标准、增量计划、工时估算、失败策略。

### 示例：邮箱验证器任务

```markdown
### Task-002：邮箱密码格式验证器

**描述**：实现 EmailValidator 和 PasswordValidator，提供纯函数校验邮箱格式和密码强度，被登录/注册表单复用。
**关联需求**：specs/auth.md §3.2 输入实时校验。→ Agent：读取 specs/auth.md 确认校验规则。
**前置依赖**：Task-001（项目骨架）。→ Agent：前置未完成时停下来先完成依赖。

**工时估算**：0.3 人天
- 基础：0.2 人天（S）
- 缓冲：0.2 × 20% × 1 = 0.04 人天（技术风险 - 低）
- 总计：0.24 人天
→ Agent：缓冲计算规则见 `references/risk-classification.md`。

**涉及文件**：
- `core/validation/EmailValidator.kt` — 新增，邮箱正则校验
- `core/validation/PasswordValidator.kt` — 新增，密码强度校验
- `core/validation/EmailValidatorTest.kt` — 新增，单元测试
- `core/validation/PasswordValidatorTest.kt` — 新增，单元测试

**验收标准**：
- **邮箱格式校验**：当输入合法邮箱地址时返回 true，输入非法格式返回 false。验证方式：EmailValidatorTest 覆盖合法/非法/边界值。
- **密码强度校验**：当密码少于8字符或不含大小写字母和数字时返回 false。验证方式：PasswordValidatorTest 覆盖合法/弱密码/边界值。

**增量计划**：
- [ ] **增量 1**：EmailValidator
  - 做什么：实现正则校验逻辑
  - 交付：EmailValidator 类 + 单元测试
  - 对应验收标准：邮箱格式校验
  - 完成判定：`./gradlew test --tests "*EmailValidatorTest*"` 通过 && `./gradlew assembleDebug` 无错误

- [ ] **增量 2**：PasswordValidator
  - 做什么：实现强度校验逻辑
  - 交付：PasswordValidator 类 + 单元测试
  - 对应验收标准：密码强度校验
  - 完成判定：`./gradlew test --tests "*PasswordValidatorTest*"` 通过 && `./gradlew assembleDebug` 无错误

**失败策略**：见 tasks.md 全局约定 — 连续 2 次失败 → debugging，3 次 → explore，4 次 → 报告用户。
```

### 排序与检查点

按阶段组织，每 2-3 个任务为一个阶段。同一阶段内无文件交集且无共享状态的任务标注"可并行"并说明具体依据。每个检查点必须有可执行的验证命令。

总工期 = 关键路径上所有任务工时之和。

### 复杂度分级

| 大小 | 文件数 | 人天 | 典型场景 | 建议 |
|------|--------|------|----------|------|
| XS | 1 | ≤0.25 | 单方法、简单UI、文档 | 无需拆分 |
| S | 1-3 | 0.25-0.5 | 单组件、单API端点 | 无需拆分 |
| M | 3-4 | 0.5-1.5 | 功能切片、多方法 | 理想粒度 |
| L | 5-7 | 1.5-3 | 多模块集成、复杂算法 | 尽量拆分 |
| XL | 8+ | — | 全栈功能、大型重构 | **必须拆分** |

**调整规则**：遇到使用新技术、依赖外部接口、高风险任务、团队不熟悉领域时，复杂度提升 1 级。

**拆分信号**：验收标准 > 3 条 → 按行为拆；任务标题包含两个独立行为 → 拆；涉及多个独立子系统 → 按业务流拆；预估 > 1.5 人天 → 评估拆分。文件数只作为复杂度信号，不是硬门槛；拆分不得破坏可构建、可测试的端到端切片。

### 并行规则

**安全并行**：独立功能模块、独立特性切片、已实现特性的测试。

**必须顺序**：数据库 migrations、共享状态更改、依赖链。

## 输出文件

输出到 `EdanSpec/feature/<name>/tasks.md`。

**并行组注释**：若存在可并行任务，在对应阶段标题前插入 `<!-- PARALLEL: Task-XXX, Task-YYY -->` 注释，供 task-implement 解析。

## 常见误区与反驳

| 说辞 | 真相 |
|------|------|
| "工时估不准，随便填" | 模糊估算会让后续所有排期和期望失控 |
| "任务大一点没关系，后面再拆" | 大任务 = 大风险。XL 几乎一定会失控 |
| "高风险任务先跳过" | 高风险任务应该尽早安排。先做简单的 = 把炸弹留到最后 |

## 警示信号

任务无实现契约引用、复用锚点或修改符号；任务无验收标准或标准不可测试；为满足文件数量机械切断端到端链路；所有任务都是 L/XL；无检查点或检查点无可验证条件；实施顺序未标注并行依据。

## 验证

> 注意：验证清单是完成后的自检列表，与验收标准（任务的定义性描述）不同。

- [ ] 每个任务都有可自动化的验收标准（三段式：触发条件、期望结果、验证方式）
- [ ] 每个任务引用真实实现契约 ID，并包含复用锚点、修改符号、失败语义和修改边界
- [ ] `review/detail.md` 的每个 IC-FLOW/IC-VERIFY 都映射到至少一个任务，阻塞项未被转成编码任务
- [ ] 每个任务都有增量计划，按依赖顺序排列
- [ ] 每个任务都有工时估算，计算规则正确
- [ ] 任务依赖关系已识别
- [ ] 任务按可验证行为切片，没有因文件数限制破坏端到端链路
- [ ] 每个阶段有检查点，检查点有可执行验证命令
- [ ] 可并行的任务标注了"可并行"及具体依据，并在阶段前插入了 `<!-- PARALLEL: Task-XXX, Task-YYY -->` 注释
- [ ] 失败策略已说明

## 完成后引导

1. 报告任务拆分结果（任务数量、总工时估算、关键路径）
2. 提示用户：**"任务已拆分完毕。要现在开始实现吗？使用 `task-implement` 技能按任务逐步开发，TDD开发,原子提交,自动验证。"**
3. 如果用户同意，引导调用 `task-implement` 技能开始执行
