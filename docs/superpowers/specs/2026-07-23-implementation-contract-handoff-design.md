# EdanSpec 实现契约交接设计

## 目标

在不增加新的人工评审阶段的前提下，将现有 `review/detail.md` 升级为 AI 可直接消费的实现契约，并让 `task-plan`、`task-implement` 强制传递和加载该契约，减少方案到编码之间的信息丢失。

## 已选方案

沿用现有产物链路：

```text
proposal/specs/design
  -> review/solution.md
  -> review/detail.md（实现契约）
  -> tasks.md
  -> task-implement
```

不新增独立 Skill 或新的状态文件。`review/detail.md` 仍由 `design-review` 生成，但内容从通用类/方法设计改为实现合同。

## 设计约束

1. `solution.md` 继续服务于人类评审，不堆积代码执行细节。
2. `detail.md` 必须包含真实代码基线、复用证据、文件与符号、字段映射、生命周期、失败语义、工程接入和验证命令。
3. `task-plan` 必须按可验证业务行为切片，不再用固定文件数切断跨层链路。
4. `tasks.md` 中每个任务必须引用实现契约，并保留复用锚点、允许/禁止修改范围和失败语义。
5. `task-implement` 开始任务前必须加载关联 spec、实现契约和项目知识地图，并验证代码锚点仍然存在。
6. UI 功能必须有自动截图/视觉回归命令，或明确保留人工视觉验收为未完成项，不得静默跳过。
7. Claude Code 与 OpenCode 分发目录保持相同合同。

## 实现契约结构

`review/detail.md` 固定包含八章：

1. 代码基线与现有资产
2. 需求到代码追踪
3. 文件与符号级变更
4. 端到端数据契约
5. 生命周期、状态与线程
6. 业务流实现合同
7. 工程接入
8. 验证合同与实现门禁

所有新增模块、类型、接口和依赖都必须通过“复用 → 扩展 → 新增”判定。现有代码证据不足或存在协议冲突时，必须形成阻塞项，不能进入任务实现。

## 任务交接

任务卡新增以下强制字段：

- 实现契约引用
- 复用锚点
- 修改符号
- 输入、输出与副作用
- 失败语义
- 允许修改范围
- 禁止修改范围
- 协议/字段映射

`task-implement` 以 `tasks.md` 为进度事实来源，但以关联 spec 和 `review/detail.md` 为行为与技术合同来源。发现代码与合同漂移时，先更新上游设计和任务，再编码。

## 验证策略

新增结构测试，覆盖两套分发目录：

- 实现契约八章完整。
- 任务规划包含合同编译和必填字段。
- 固定三文件/0.5 人天限制被移除。
- 实现阶段强制读取 contract/spec/context。
- 代码锚点漂移会阻塞实现。
- UI 视觉验收不能被静默跳过。
- Claude Code 与 OpenCode 关键文件保持一致。

最后运行仓库现有 Python 和 Node 测试、Markdown/差异检查，并进行一次临时 feature 产物的干运行校验。
