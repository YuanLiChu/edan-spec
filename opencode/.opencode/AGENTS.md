# Agent 基础规范

## 核心铁律

以下六条原则在任何情况下都必须遵守：

### 1. 亮出假设

需求模糊时不要主观臆断，先将假设明确列出：

```
我做的假设：
1. ...
2. ...
→ 请确认是否正确。
```

### 2. 有疑问就停

碰到矛盾或冲突时：暂停 → 说明问题 → 给出选项 → 等待回复再继续。

**正确：** "文档要求 X，代码实现是 Y，以哪个为准？"
**错误：** 自行猜测并选择一个继续推进。

### 3. 该反对就反对

方案存在明显问题时：指出问题 → 量化后果 → 提供替代方案 → 若用户坚持则执行。

明知有风险却不予提醒，是最严重的失职。

### 4. 能简单别复杂

默认倾向是把问题简单化，需时刻反问：代码还能更少吗？这个抽象值得吗？

简单可行的方案优于精巧过度设计的方案。

### 5. 只做分内事

仅修改被要求修改的内容：不删除不理解的代码、不改动无关代码、不重构相邻系统、不添加额外功能。

聚焦于当前任务，保持变更范围最小化。

### 6. 拿证据说话

完成不等于正确。通过测试通过、构建成功、数据验证来证明，主观判断不能作为正确性的依据。

## 行为准则

- **项目技能优先** — 当项目定义了 `skills/` 时，对应场景必须调用相应 skill，不得以通用能力替代。例如：生成方案文档时调用 `create-spec`，而非 `/plan`
- **技能是流程不是建议** — 严格按步骤执行，不得跳过验证环节
- **不确定就先出方案** — 复杂任务先产出方案文档，经确认后再编码
- **单 Agent 优先** — 仅对可独立执行的子任务进行并行扇出，完成后合并回主流程
- **失败不盲试** — Skill 内部错误由 Skill 自行消化；构建或测试失败时定位根因再修，不盲目重试；连续 3 次相同错误则停止并报告用户

## 规范加载

编码前按文件后缀自动加载对应规范。所有 Git 操作额外遵循 `docs/git-conventions.md`：

| 文件类型 | 加载规范 |
|---------|---------|
| `.kt` / `.kts` | `rules/kotlin/` + `rules/common/` 下所有 `.md` |
| `.java` | `rules/java/` + `rules/common/` 下所有 `.md` |
| 其他语言 | `rules/common/` 下所有 `.md` |

## 变更管理

所有代码变更通过变更目录（`EdanSpec/feature/{timestamp}-{topic}/`）进行追踪与管理：

- **一个变更 = 一个目录** — 聚合 proposal、specs、design、tasks 等交付物
- **状态驱动** — 从文件系统恢复上下文，不依赖会话记忆
- **tasks.md 是唯一进度来源** — 采用 checkbox 格式，驱动 implement 流程
- **产物状态从文件系统事实推导** — 不写入 status.json，脚本实时计算
- **完成后归档** — 移至 `EdanSpec/archive/`

新会话启动时的上下文恢复流程见"上下文管理"章节。

## 上下文管理

**在恰当的时机加载恰当的信息，避免上下文不足或过度膨胀。**

### 策略选择

根据任务复杂度选择加载策略：

| 策略 | 适用场景 | 加载范围 | 预算 |
|------|---------|---------|------|
| **精准** | 单文件修改、bug 修复 | 1–3 个文件，仅相关段落 | 不超过 500 行 |
| **增量** | 同领域多文件修改 | 规则 + 设计文档 + 相关文件 | 不超过 1500 行 |
| **全量** | 跨系统变更、架构重构 | 各层级完整加载 | 不超过 3000 行 |

选择路径：单文件且目标明确 → 精准 | 同领域多文件 → 增量 | 跨系统/架构级 → 全量

### 上下文分层

按信息粒度从粗到细组织，每次只加载当前需要的层级：

```
┌─────────────────────────────────────┐
│  1. 规则文件（CLAUDE.md 等）        │ ← 始终加载
├─────────────────────────────────────┤
│  2. 架构/设计文档                   │ ← 按功能/会话加载
├─────────────────────────────────────┤
│  3. 相关源文件                      │ ← 按任务加载
├─────────────────────────────────────┤
│  4. 错误输出/测试结果               │ ← 出错时加载
├─────────────────────────────────────┤
│  5. 会话历史                        │ ← 自然累积，适时重置
└─────────────────────────────────────┘
```

### 加载规则

**开始前：** 读取当前阶段相关决策文件的关键章节（不读全文）→ 读取需修改的源文件 → 查找代码库中的相似模式作为风格参考。

**执行中：** 出错时只加载具体错误信息（不粘贴全量日志）→ 一次只关注一个文件 → 先读取再决定是否修改。

**跨阶段切换：** 完成后释放实现细节（见释放策略）→ 从任务文档读取下一阶段信息 → 涉及大量新代码阅读时考虑开启新会话。

### 释放策略

满足以下任一条件时，必须清理当前上下文：

| 触发条件 | 操作 |
|---------|------|
| 当前增量完成并已提交 | 释放源文件内容、错误输出，保留任务文档 |
| 切换至下一阶段 | 释放当前阶段全部实现细节，仅保留决策文件 |
| 上下文接近预算上限 | 将已完成的中间结果写入文件，用摘要替代全文 |
| 生成长文档或多文件代码 | 逐章执行：生成 → 保存 → 展示摘要 → 确认 → 释放 → 下一章 |

### 恢复模式

新会话启动或中断恢复时，按以下检查清单重建上下文：

1. 检查 `EdanSpec/feature/` 是否存在活跃变更（`status.json` 中 `state: "active"`）
2. 从文件系统确认已完成的交付物（proposal.md / specs/ / design.md 存在且非空）
3. 读取 `tasks.md` 确认待办任务
4. 仅加载与下一步任务相关的源文件

无活跃变更时，进入正常流程。

### 冲突处理

信息冲突时不要自行选择，向用户报告并提供选项：

```
CONFUSION:
方案设计要求 REST API，但现有代码使用 GraphQL（参考：src/graphql/user.ts）。

选项：
A) 跟随方案设计 — 新增 REST 接口
B) 跟随现有模式 — 使用 GraphQL
C) 请用户决策
```

| 冲突类型 | 处理方式 |
|----------|----------|
| 方案与代码不一致 | 报告冲突，提供选项 |
| 任务规划缺少信息 | 暂停并询问 |
| 规格未覆盖边界场景 | 查找现有代码先例，无则询问 |

### 内联计划

编码前用一两行说明思路，给用户纠偏的机会：

```
Plan:
1. 编写 createTask 的失败测试
2. 实现最小版本让测试通过
3. 重构：提取 id 生成逻辑
→ 开始执行，除非你另有指示。
```

### 警示信号与对策

| 信号 | 对策 |
|------|------|
| 虚构不存在的 API 或方法 | 立即停止，通过 grep 验证 API 是否存在 |
| 加载了大量文件但只修改了小功能 | 切换为精准策略，减少加载范围 |
| 使用了项目中不存在的模式 | 回到加载规则，重新查找实际代码模式 |
| 默默选择了冲突的一种解释 | 回退到冲突处理流程，报告并等待决策 |

## 测试与质量

### 覆盖率工具配置

**任务分解时必须包含覆盖率工具的配置步骤。** 在编写代码前，先确认覆盖率工具已就绪：
- **全新项目初始化** — 初始化工程时必须同步配置覆盖率工具（如 JaCoCo、pytest-cov 等），不得留到后面补
- **已有项目** — 检查是否已配置覆盖率工具；如未配置，在 tasks.md 中增加「配置覆盖率工具」任务，编码前先完成
- 覆盖率报告必须能在构建或测试命令中一键生成

不得在覆盖率工具未就绪的情况下开始编写测试。

### 测试覆盖率基线

| 指标 | 基线 |
|------|------|
| 行覆盖率 | ≥ 80% |
| 分支覆盖率 | ≥ 70% |
| 主要路径 | 100% |

低于基线时需补充测试，不得为凑数字编写无意义测试。

### 编写原则

- **行为优先** — 验证行为结果，不验证内部调用；断言最终状态，而非中间过程
- **TDD 循环** — RED（失败测试）→ GREEN（最小实现）→ REFACTOR（重构优化）
- **AAA 三段式** — Arrange（准备数据）→ Act（执行操作）→ Assert（断言结果）
- **单一职责** — 每个测试只验证一个行为，命名清晰描述意图
- **DAMP 优于 DRY** — 可读性优先于复用，每个用例自包含
- **Bug 先复现** — 修复前先编写复现测试，确认失败后再修复
- **Mock 最小化** — 优先真实实现，仅在外部依赖或不可控副作用时使用 Mock
- **测试隔离** — 用例间不共享状态，单独运行与批量运行结果一致
- **不测第三方** — 只测试自己的业务逻辑，不验证框架或库的行为

### 覆盖场景

每个公共方法或函数至少覆盖以下场景：

| 场景 | 说明 | 示例 |
|------|------|------|
| **正常路径** | 输入合法，预期正常返回 | 正确用户名密码登录成功 |
| **边界值** | 空值、零值、最大/最小值、空集合 | 分页参数为 0 或 Integer.MAX_VALUE |
| **异常路径** | 输入非法，返回明确错误 | 负数金额、不存在的 ID |

## 退出条件

满足以下任一条件时，Agent 应停止执行并等待用户确认：

- 当前增量已完成，等待验证或提交
- 遇到无法自行判断的决策点
- 构建或测试反复失败且无法定位根因
- 方案变更导致已有测试或代码需要返工
- 上下文预算达到上限且无法通过释放策略缩减
- 涉及破坏性变更（数据库迁移、API 接口变更、配置变更）

## 权限边界

以下操作 Agent 不得自行决定，必须获得用户明确授权：

- 删除文件或目录
- 修改数据库 Schema 或执行数据迁移
- 变更外部 API 接口定义
- 修改配置文件中影响其他服务的参数
- 提交包含敏感信息的代码（密钥、凭证、个人信息）
- 向外部服务发送请求（邮件、消息推送、API 调用）
- 修改 CI/CD 配置或发布流程

## 常见陷阱

1. 未验证假设就直接编码
2. 遇到异常仍继续推进
3. 发现不一致却未上报
4. 重要决策缺少利弊分析
5. 方案有明显问题仍予通过
6. 代码过度设计
7. 超出任务范围修改代码
8. 删除不理解的代码
9. 跳过方案设计直接编码
10. 以"看起来对"为由跳过验证

## 常见误区与反驳

见 `docs/anti-patterns.md`。六类误区：太简单、后面补、差不多、不用确认、效率优先、场景特殊。核心原则：**识别到误区时立即停止，对照真相反思。**
