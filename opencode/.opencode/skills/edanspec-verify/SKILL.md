# 结构化验证

feature 归档前的最终关卡。"拿证据说话"——但结构化告诉你**需要什么证据**。

 **职责**：本 skill 负责准备上下文 → 启动验证代理 → 根据结果判定归档结论。检查项定义在正文中，代理通过读取 SKILL.md 执行。
 **边界**：verify 只负责验证和写入报告文件。delta spec 合并和文件移动由 `edanspec-archive` 负责。动态测试和覆盖率由 `edanspec-task-implement` 的 5 项自动化验证完成，verify 仅做静态检查。

## 三维度

每个维度有固定的检查步骤，代理必须逐项执行。

### 完整性 — 任务与场景覆盖

1. **tasks.md checkbox 统计**
   - 读取 `tasks.md`，逐行扫描 checkbox 格式 `- [ ]` 和 `- [x]`
   - 统计未完成（`- [ ]`）任务数量
   - 对每个未完成任务：grep 代码库中相关函数/文件，确认是否实际已实现
   - 未完成任务且代码也不存在 → CRITICAL
   - 未完成任务但代码已实现 → SUGGESTION（checkbox 漏勾）

2. **spec 场景覆盖**
   - 读取 `specs/*.md`，提取所有 WHEN/THEN 场景（或需求条目）
   - 对每个场景：grep 相关函数名、文件名、关键字，寻找对应代码分支
   - 找不到任何代码证据 → IMPORTANT

### 正确性 — 实现与逻辑验证

> 本维度做**静态结构 + 逻辑完整性检查**。动态测试运行和覆盖率检测由 task-implement 的自动化验证完成，verify 不再重复。

1. **spec 需求逐一对照**
   - 对每个 spec 需求/场景：
     - 通过 design.md（如存在）找到需求与代码文件的映射关系
     - 找到对应代码文件（grep 需求关键字、函数名、类名）
     - 读取代码，确认实现了需求的关键逻辑
     - 检查 WHEN/THEN 中的条件分支是否存在（if/else/try-catch）
     - 检查边界条件（空值、零值、最大值）是否有处理代码

2. **输入验证与数据流检查**
   - 对每个公开函数/方法的入口参数：
     - 检查是否有类型约束或参数校验（null check、范围检查、格式验证）
     - 无校验且参数来自外部输入（API 请求、用户输入、文件读取）→ IMPORTANT
   - 对关键数据流转路径：
     - 检查错误返回值是否被处理（非 void 返回值是否有判断/传播）
     - 异常是否被捕获或声明抛出（try-catch / throws）
     - 完全忽略错误或吞掉异常（空 catch 块、仅 print 不传播）→ IMPORTANT

3. **测试文件存在性与场景覆盖检查**
   - 找出本次变更新增的功能文件（对比 spec 中提到的文件路径）
   - 确认每个新增功能文件有对应的测试文件（同名或约定命名）
   - 打开测试文件，检查测试用例是否覆盖了 spec 中定义的正常路径 + 异常/边界场景
   - 注意：此处检查的是"测试是否覆盖了 spec 定义的场景"，而非"测试是否通过或覆盖率数值"（后者由 task-implement 自动化验证负责）
   - 新增功能无对应测试文件 → IMPORTANT
   - 测试文件存在但未覆盖 spec 中的异常/边界场景 → SUGGESTION

4. **接口契约检查**
   - 检查 spec 中定义的输入输出类型、字段名称、返回值格式
   - 对比代码中的实际签名和数据结构
   - 接口签名不一致（缺必填字段、返回类型不匹配）→ CRITICAL
   - 字段命名不一致但语义等价 → SUGGESTION

### 一致性 — 设计与规范遵循

1. **设计决策对照**
   - 读取 `design.md`，提取所有设计决策（技术选型、架构决策、接口定义）
   - 逐个检查代码是否遵循：
     - 选型了 A 但代码用了 B → IMPORTANT
     - 决策被忽略但代码中无说明 → IMPORTANT
     - 设计已更新或代码有合理替代 → 通过

2. **项目规范遵循**
   - 读取 `AGENT.md` 核心铁律（能简单别复杂、只做分内事）— 检查是否有过度抽象、多余功能、无关改动
   - 读取 `rules/` 目录下对应语言的 `.md` 规则文件 — 检查新增代码是否违反具体规则
   - "多余功能"：spec 和 design.md 中未提及但代码中新增的公开函数/端点 → IMPORTANT
   - "无关改动"：git diff 中超出 feature 涉及文件列表的变更 → IMPORTANT
   - 仅风格或规范偏离、不影响功能 → SUGGESTION

3. **过度设计量化判定**
   仅凭"感觉代码复杂"不够，用以下量化指标判断：
   - **抽象层超限**：超过 3 层间接调用（A→B→C→D→实现），中间层仅做转发（无条件判断、无数据变换、无副作用）→ SUGGESTION
   - **接口过剩**：为只有 1 个实现类的接口定义了接口，且无测试 Mock 需求 → SUGGESTION
   - **工厂/建造器滥用**：仅创建 1 种类型对象却引入工厂模式 → SUGGESTION
   - **通用化过早**：单处使用的逻辑提取为通用工具/基类 → SUGGESTION
   - 上述情况但有明确记录的设计理由（注释或 design.md 说明）→ 通过

## 级别定义

严重度用于判定发现问题的优先级和对归档的影响。各维度检查步骤中使用以下级别。

| 级别 | 含义 | 归档影响 |
|------|------|---------|
| **CRITICAL** | 与 spec 明确不一致，会导致功能不可用或行为偏离预期 | 必须修复，否则不能归档 |
| **IMPORTANT** | 应该解决的问题，影响质量但不会直接导致功能失效 | 应该修复，用户确认后可归档 |
| **SUGGESTION** | 可选改进，不影响功能正确性 | 可直接归档 |

**级别使用规则：**
- 各维度检查步骤直接标注级别，代理发现对应问题时按标注写入报告
- 去重规则中同一问题跨维度出现时，仅在最先发现的维度记录一次，级别不变
- 检查步骤未覆盖的边界情况，代理可按上表定义自行判断级别并注明原因

## 执行约束

代理在每一步都必须遵守的规则。

### 去重

同一问题在多个维度交叉出现时，只在最先发现的维度记录一次：
- 未完成任务但代码已实现 → 仅完整性记录为 SUGGESTION（checkbox 漏勾）
- 未完成任务且代码也不存在 → 仅完整性记录为 CRITICAL
- spec 场景无代码证据 → 仅完整性记录为 IMPORTANT

### 搜索策略

按顺序递进，前一层无结果才进下一层：

1. **精确匹配** — 函数名、类名、文件名 grep（含命名变体）
2. **语义匹配** — 搜注释、字符串、日志。例：spec "用户不存在返回 404" → `"user not found"` / `"404"` / `"用户不存在"`
3. **LSP 符号** — `goToDefinition` / `findReferences`

声明式配置只查键值。三层均无结果 → 记"无代码证据"，继续下一项。

### 异常处理
- grep 结果过多：改用 LSP 符号搜索或限定变更文件范围
- 无对应语言规则文件：跳过规范检查，报告注明
- 无法理解的检查项：跳过并注明原因，继续下一项

### 报告书写
- 每个发现必须含文件位置（文件:行号）和具体修复建议
- 禁止笼统描述，给出具体文件名、行号、代码片段

## 验证流程

### 步骤 1 — 准备上下文

1. **扫描已有文件**：检查 `tasks.md`、`specs/*.md`、`design.md`、`proposal.md`（不存在的跳过）。
2. **记录产物缺失**：对每个不存在的文件，在报告中注明"缺少 XXX 文档，该维度部分检查项无法执行"，但**不得跳过整个维度**。
3. **确定报告输出**：路径含 `EdanSpec/feature/` 则写入 `{feature-dir}/verify-report.md`，否则仅输出到控制台。
   该参数传给步骤 2 的验证代理，代理根据此参数决定是否写入文件。

### 步骤 2 — 执行验证

通过 task 工具启动通用代理，传入以下提示词：

```
task({
  description: "结构化验证",
  prompt: "对 feature 执行三维度验证（完整性/正确性/一致性）\nFeature 目录：{feature-dir}\n已有文件：{existing-files}（步骤 1 已扫描，仅列出存在的文件）\n报告输出：{report-target}（步骤 1 已确定，不得自行更改）\n\n第 1 步 — 读取本 SKILL.md 全文，了解三维度的检查步骤、级别定义和执行约束。\n\n第 2 步 — 加载上下文：仅读取"已有文件"中列出的文件，不存在的文件跳过。\n\n第 3 步 — 全量执行三维度检查（严格按顺序执行）：\n         三个维度必须全部执行，不得因缺少文档而跳过整个维度。\n         某个检查步骤依赖的文档不存在时，跳过该步骤并在 findings 中记录：\n         - 维度: <完整性|正确性|一致性>\n         - 检查项: <对应 SKILL.md 中的检查步骤编号，如 "正确性.2">\n         - 级别: IMPORTANT\n         - 文件:行号: N/A\n         - 问题: 缺少 XXX 文档，<检查步骤名>无法执行\n         - 建议: 补充该文档\n         有文档的检查项正常执行，发现记录到 findings 列表中。\n         findings 列表格式：\n         - 维度: <完整性|正确性|一致性>\n         - 检查项: <对应 SKILL.md 中的检查步骤编号>\n         - 级别: <CRITICAL|IMPORTANT|SUGGESTION>\n         - 文件:行号: <具体位置>\n         - 问题: <一句话描述>\n         - 建议: <具体修复建议>\n         无问题的检查项不记录，跳过。\n\n         去重：记录前检查 findings 列表中是否已有相同问题（同一代码位置、同一问题描述），\n         如有则跳过，不在多个维度重复记录。\n\n第 4 步 — 按 SKILL.md 的"报告格式"输出报告。\n         报告必须包含 findings 列表中所有条目，按级别分组。\n         缺少的文档在报告中注明，但不标注"未执行"。\n         如果报告输出路径为文件，写入该文件；否则输出到控制台。\n\n全局约束：\n- 搜索策略：精确匹配（函数名/类名/文件名）→ 语义匹配（注释/字符串/日志）→ LSP 符号搜索\n- 声明式配置（YAML/JSON）只检查键名和值，不搜代码分支\n- 搜不到 → 记录"无代码证据"，继续下一项\n- grep 结果过多 → 改用 LSP 符号搜索或限定变更文件范围\n- 无对应语言规则文件 → 跳过规范检查，报告注明\n- 无法理解的检查项 → 跳过并注明原因，继续下一项\n- 每个发现必须有文件位置和修复建议，禁止笼统描述",
  subagent_type: "general"
})
```

**上下文隔离**：独立子进程执行，保证验证的客观性和独立性。

### 步骤 3 — 判定结论

验证代理执行完毕后，根据结果判定归档结论：

| 条件 | 结论 | 处理 |
|------|------|------|
| CRITICAL > 0 | 自动修复 | 修复所有 CRITICAL → 删除 `verify-report.md` → 重新执行 verify |
| CRITICAL = 0, IMPORTANT > 0 | 可归档（需用户确认） | 报告保留，引导用户决定是否处理 IMPORTANT |
| 全部通过 | 验证通过，可以归档 | 引导归档 |

> **与 task-implement 的一致性**：verify 发现 CRITICAL 时自动修复，与 task-implement 步骤 6 中 code-review、security-review、verify 三关卡统一采用"自动修复 CRITICAL → 删除报告 → 重跑"策略。`edanspec-archive` 在遇到 CRITICAL 时拒绝归档，因为归档前 verify 必须已 passed。

## 报告格式

验证完成后，按步骤 1 中确定的报告输出方式输出：

```markdown
# 验证报告：{feature-name}

## 摘要

| 维度         | 状态              |
|--------------|-------------------|
| 完整性       | X/Y 任务, N 需求  <!-- X=已完成数, Y=总数; N=spec 场景总数 --> |
| 正确性       | M/N 需求已覆盖    <!-- M=有代码覆盖的需求数, N=spec 需求总数 --> |
| 一致性       | 遵循设计 / N 处偏离 |

> 某维度缺少依赖文档时，状态栏注明"部分检查受限（缺少 XXX）"，如"部分检查受限（缺少 design.md）"。

## 问题摘要

| 级别 | 数量 | 说明 |
|------|------|------|
| CRITICAL | N | 必须解决，否则不能归档 |
| IMPORTANT | N | 应该解决 |
| SUGGESTION | N | 可选改进 |

**CRITICAL（必须解决，否则不能归档）**

- `文件:行号` 未完成任务且无代码实现：<任务描述>
  → 建议：完成任务或标记为已完成

- `文件:行号` 接口签名不一致：<具体差异，如缺必填字段/返回类型不匹配>
  → 建议：修正签名使其与 spec 一致

## IMPORTANT（应该解决）

- `文件:行号` spec 需求未覆盖：<需求名称>
  → 建议：实现该需求或从 spec 中移除

- `文件:行号` 未遵循设计决策：<决策项>
  → 建议：修改实现或更新 design.md

## SUGGESTION（可选改进）

- `文件:行号` 代码风格偏离：...
  → 建议：调整为项目现有模式

## 结论

- 有 CRITICAL → "发现 N 个 CRITICAL 问题，自动修复中"。修复后删除报告，重新执行 verify
- 仅有 IMPORTANT → "无 CRITICAL 问题，N 个 IMPORTANT 建议归档前处理"
- 全部通过 → "验证通过，可以归档"
```

## 常见误区与反驳

> 通用误区见 `AGENT.md`。

| 说辞 | 真相 |
|------|------|
| "代码能跑就不用验了" | 能跑 ≠ 完整。可能漏了异常处理和边界条件 |
| "小改动不需要验证" | 小改动最难回滚，漏一个 spec 就是生产 bug |
| "测试绿了就够了" | 测试绿 = 写了的测试通过了。spec 里没被写成测试的需求呢？ |

## 警示信号

- 未全量执行三维度就声称"验证通过"
- 报告中只有 SUGGESTION，没有认真查 CRITICAL/IMPORTANT
- 没有给出具体文件位置和建议
- 批准了有 CRITICAL 问题的 feature 归档

## 验证

- [ ] 三维度均已验证（或有降级说明）
- [ ] 每个发现都有文件位置和修复建议
- [ ] CRITICAL 问题已全部解决（否则拒绝归档）
